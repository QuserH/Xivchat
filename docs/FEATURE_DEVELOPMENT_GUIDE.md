# 艾欧泽亚终端后续功能开发规范

适用工程：`XIVChat-source/EorzeaPhoneAndroid`

日期：2026-09-06

## 1. 总原则

1. 先确定功能边界，再写代码。新功能不得继续整段追加到 `ShizhijiaScreens.kt`、`AetherphoneParityScreens.kt`、`PhoneModels.kt` 或 `CraftScreens.kt`。
2. 路由、状态、数据、渲染分层；页面只负责组合，不负责协议解析、文件读写或大对象转换。
3. 保持现有路由名、持久化键和网络协议兼容。需要改变协议时，必须同时更新 Android 与 Dalamud 插件并做回归测试。
4. 列表滚动是高频路径：禁止在 item lambda 中做网络请求、同步文件读写、全量排序、图片解码或大集合复制。
5. 所有可复用逻辑只保留一个实现；不要为同一含义再创建第二套颜色、时间格式、缓存或状态字段。

## 2. 目录与职责

```text
app/src/main/java/com/quserh/eorzeaphone/
├─ data/                         网络、数据库、缓存、通知、插件连接
├─ ui/
│  ├─ *Screen.kt                 一个完整页面或一个明确页面族
│  ├─ *Components.kt             可复用视觉组件和列表行
│  ├─ *State.kt                  页面状态容器、筛选状态、滚动状态
│  ├─ *Rendering.kt              文本解析、布局缓存、图标渲染
│  └─ *Models.kt                 稳定的 UI 数据模型和默认值
└─ craft/
   ├─ data/                      配方、BOM、制作计算和持久化
   └─ ui/                        制作页面与制作组件
```

当前已落地的示例：

- `PhoneModelTypes.kt`：手机 UI 模型与默认数据。
- `ChatSearchSupport.kt`：聊天搜索 key、稳定列表 key 和定位缓存。
- `ChatBubbleRendering.kt`：气泡文本解析、内联图标和布局缓存。
- `CraftListComponents.kt`：制作清单列表组件。
- `CraftStatsStore.kt`：按角色分区、按游戏职业 ID 保存的统一制作属性。
- `CraftStatsSettings.kt`：独立属性设置弹层，只有输入草稿留在 UI。

石之家现有 Feed、招募、幻化与搜索状态暂时留在原文件中，不强行拆高耦合路由；新增独立视觉功能应另建文件。

## 3. 新功能落地流程

### 3.1 先写边界说明

开发前在 PR 或提交说明中写清楚：

- 入口路由和返回路径。
- 页面状态字段及其生命周期（页面内、返回保留、应用重启保留）。
- 数据来源（插件、HTTP、数据库、本地偏好）。
- 空、加载、失败、离线和权限不足状态。
- 是否需要通知、后台任务或迁移旧数据。

### 3.2 数据层

- API、MessagePack、SQLite 和文件读写只能放在 `data/` 或 `craft/data/`。
- 网络模型与 UI 模型分开；在 Repository/Mapper 中完成转换。
- 所有请求提供超时、取消、错误类型和重试上限；不得无限重试。
- 需要长期保存的数据使用版本化 schema，并提供旧版本读取或迁移。
- 大图、图标和 HTML 使用统一缓存；列表只拿轻量元数据，详情页再取大内容。

### 3.3 状态层

- 页面状态放入独立 `*State.kt`，使用一个稳定的状态容器，避免多个 Composable 各自复制同一状态。
- 进入详情再返回仍需保留的数据，放在页面族的 hoisted state 或导航拥有的 state 中。
- 派生值使用 `derivedStateOf` 或明确的 mapper；不要在每次重组中反复过滤、排序和构造 Map。
- 状态更新要有单向路径：事件 → state/repository → UI。不要从 UI item 直接修改多个全局集合。
- 输入框草稿、筛选、滚动锚点要明确何时清空、何时恢复，并覆盖返回场景。

#### 跨功能共享状态与联动

- 角色身份、插件连接、原始库存、游戏内制作状态、技能和食药数据以现有 `PhoneState` / Repository 为唯一来源；新页面必须接收既有实例，不得自己新建连接或长期保存第二份可写业务状态。
- 制作清单、购物车、BOM、库存位置与工作台必须共享同一个 `CraftAppState` 内的 `lists`、`cart`、`repo` 和 `session`。文件拆分只移动职责，不改变状态所有者；子组件通过参数读状态并调用原有方法。
- 允许 Mapper 产生制作侧只读库存视图，但其输入必须来自 `PhoneState.craftRawInventory`；快照变化时统一更新，不能由每个列表自行同步或合并。
- 跨功能写入通过同一 state/Repository 方法完成，并验证至少一条联动路径，例如库存同步后材料持有数和位置同时更新、清单改数量后 BOM 和工作台选项一致、远程制作新帧只更新当前会话。
- 模拟制作不模拟真实时间 CD，技能只由 `CraftSimulation.canUse` 的制作规则判定；远程制作可用性由插件 `canAct` 和会话终止/取消状态判定，不得拿模拟规则覆盖远程状态。

#### 制作属性与当前游戏职业

- 制作力上限、作业精度、加工精度按稳定的制作职业 ID 持久化，不能继续共用一组三项全局值，也不能以可翻译职业名或页面列表下标作为存储键。游戏 ClassJob ID 与配方职业编号通过唯一 Mapper 转换。
- 制作属性配置由现有共享 state/Repository 持有；设置页、工作台、模拟制作必须读写同一份职业配置。输入草稿可以在页面内暂存，但保存必须调用统一入口，不得各自创建偏好文件或第二份可写属性 Map。
- 当前游戏职业只来自插件同步的共享 `PhoneState` 数据。职业切换、重新连接或主动刷新后统一更新；设置页选择的编辑职业与当前游戏职业是不同含义，不得用编辑选择反写、猜测或覆盖游戏职业。
- 插件每次请求都重新读取当前职业及三围；动态属性不得与静态技能表一起缓存。只有当前制作职业的有效正数才能更新对应配置，旧插件缺字段、非制作职业和读取失败都不得用零值覆盖已保存配置。
- 制作力保存上限，不保存制作中消耗后的剩余值；同步值、手动模拟值与临时食药加成的优先级必须明确。模拟开始时按配方职业取得配置快照，配置编辑不回写已开始会话；远程会话继续以游戏推送为准。
- 保留旧版全局三项的兼容读取：仅在该职业尚无配置时使用旧值或默认值，迁移后不能每次启动覆盖按职业值。切换角色时不得将上一角色的实时同步值误写给新角色，持久化作用域应明确记录。
- 当前实现：属性放在 `PhoneState` 的既有角色偏好分区中，键为 `craft_stats_job_<ClassJobId>_*`。收到有效游戏值即保存（含当前食药加成的实际面板），手动保存用于离线/未同步职业；不额外叠加已包含的食药三围。游戏下一次同步可覆盖同职业手动值，已开始模拟使用启动时快照不变。
- 回归至少覆盖两个职业分别编辑与重启恢复、职业切换同步、设置与工作台联动，以及缺字段/零值不清空已有配置。

### 3.4 UI 层

- 完整页面放 `*Screen.kt`；跨页面复用的行、卡片、弹层放 `*Components.kt`。
- 复杂弹窗单独命名为 `*Sheet`、`*Dialog`，不要嵌在 500 行页面函数中。
- 统一使用项目已有主题 token、间距、圆角和图标组件；不要新增硬编码颜色。
- 列表必须提供稳定 key 和合适的 `contentType`。key 不能只使用时间戳。
- `remember` 的 key 必须对应真实输入；不可把可变大 List 直接作为无意义的 key。
- 图片使用异步加载和目标尺寸采样；不要在主线程调用 BitmapFactory 或读取文件。
- 动画必须支持减少动画设置；返回主界面时避免重复叠加页面级渐隐动画。

## 4. 性能红线

以下代码不得出现在 LazyColumn/LazyRow/Grid 的 item 内容中：

- `readText`、`writeText`、JSON 全量序列化。
- HTTP、WebView 初始化、数据库查询或 Bitmap 解码。
- 对数千条消息/物品执行 `filter + map + sorted` 的组合操作。
- 每帧修改父级列表状态，导致所有 item 重组。
- 为了显示一个字段复制整份消息、库存或配方集合。

滚动卡顿排查顺序：

1. 看 item 是否有同步 IO、图片解码和大集合分配。
2. 检查 key 是否稳定，是否因发送状态等短生命周期字段导致整行重建。
3. 检查 `remember`/`derivedStateOf` 的粒度，确保只更新受影响的行。
4. 检查返回动画和页面栈，确保没有同时保留两层可见页面。
5. 最后才调整动画时长或阴影；不要用视觉参数掩盖状态重组问题。

## 5. 路由与返回行为

- 新页面必须通过现有页面分发/返回机制进入，不得自行维护第二套路由栈。
- 返回时只 pop 当前页面；搜索结果、列表滚动位置和详情锚点按页面定义恢复。
- 取消制作、删除会话、清空历史等不可逆动作必须二次确认，并明确说明影响。
- 页面退出时取消自己的协程和监听；不得让旧页面继续消费新事件。

## 6. 缓存与存储

- 缓存分为内存 LRU、磁盘缓存和业务数据库，分别定义容量、过期策略和清理入口。
- 可复用的图标/道具元数据只保存一次，通过 ID 引用；不要在每条消息或每份清单中复制图片二进制。
- 写盘使用 IO dispatcher、临时文件替换和版本合并；高频编辑应合并写入。
- 新增持久化字段时记录 schema/version，并测试旧数据为空、损坏和升级场景。
- 提供缓存统计或清理入口，避免调试日志代替存储治理。

## 7. 插件与协议

- Android 端先兼容旧字段，再启用新字段；未知字段必须可安全忽略。
- 现有 MessagePack 数组协议只允许在末尾追加可选字段并使用新的递增 `Key`；不得插入、重排、删除或复用旧 `Key`，不得改变旧字段类型、含义或 opcode。Map 协议只追加新键。非兼容变化必须单独设计版本或新消息类型。
- 新增字段必须有缺失处理和有效性校验。Android 读取旧短帧时按长度检查后使用“未知/未提供”语义，不能把缺失的职业、三围等值当作有效零值覆盖现有共享状态与持久化数据。
- 职业与制作属性沿用现有技能列表请求/响应追加传递；解码后只更新统一共享状态，再由制作模块映射与保存，禁止为设置页新增独立请求通道或复制连接。
- 修改制作、库存、潜艇或通知协议时，先写帧/消息样例，再实现解析和状态机。
- 状态机要定义开始、进行中、完成、失败、取消、超时六类状态，避免幽灵重启和旧会话残留。
- 插件构建与 Android 构建必须分别验证；协议改动不得只依赖单端编译通过。
- 兼容测试至少覆盖旧插件响应 → 新 Android、新插件响应 → 旧解析路径，以及新旧字段混合/缺失场景；确认追加字段不会改变旧功能。

- [ ] Debug 测试、Kotlin 编译和必要的 Release/插件构建是否通过？
- [ ] staged diff 是否只包含本次改动？

## 10. 文件大小预警线

- 单个 Kotlin 文件超过 80 KB：新功能必须新建文件，不再追加。
- 超过 150 KB：安排按状态、列表、详情、弹层、视觉组件拆分。
- 超过 250 KB：禁止继续堆功能；拆分应成为当前迭代的一部分。
- 拆分优先级：纯模型/状态 → 纯渲染辅助 → 列表组件 → 弹层/详情页 → 高耦合路由。
